技术方案 · InsightFace 二次识别

P6S 摄像头人脸识别增强与噪音过滤

本方案在现有 P6S 摄像头事件链路之后、飞书通知和入场记录之前，引入 InsightFace buffalo_l 做服务器侧二次检测、质量过滤和可选二次比对，用来减少侧脸、模糊图、无效人脸和摄像头误判导致的错误提醒。

一、背景与核心结论

当前问题

摄像头自带识别存在侧脸误报、正脸不稳定、陌生人误报、抓拍人脸图模糊等问题。继续只依赖摄像头识别结果，会影响飞书提醒可信度和每日到场统计准确性。

推荐方向

第一期不替换摄像头，也不做 RTSP 全量视频流识别；先用摄像头事件作为触发源，在服务器上对事件图片做二次判断。这样改动范围小、计算压力可控、回滚简单。

已确认前提：用户已确认可以使用 InsightFace buffalo_l 模型。本方案基于 buffalo_l 作为默认模型设计，部署时仍需要把模型文件放在服务器私有目录，不进入 Git 仓库。

二、目标与非目标

目标

  • 对每条 FaceReco 事件保存后的 BackgroundImage 做人脸检测，判断是否真的有人脸；当背景图无人脸，或单人脸 Gallery 相似度低于阈值时，再用 CaptureImage 做 fallback 复核。
  • 过滤侧脸、过小人脸、模糊图、低置信度检测等噪音事件。
  • 可选启用二次人脸比对，用服务器侧人脸特征库纠正摄像头把已知人员识别成陌生人的情况。
  • 保留当前双图飞书链接、入场记录、日报和去重逻辑的主流程，只在其前面增加一层可开关的二次判断。
  • 以 shadow 模式先上线验证，收集对比结果，不立刻影响飞书通知和入场统计。

非目标

  • 不修改摄像头人脸抓拍、推送、录像、脸库等配置。
  • 不在第一期接管 RTSP 视频流，不做连续帧识别。
  • 不训练新模型，不做活体检测，不做人脸属性分析产品化展示。
  • 不把会员、教练、员工原始人脸图片或生成的 embedding 文件提交到 Git。
  • 不改飞书机器人密钥、远程域名、图片 token 链接机制。

三、当前链路与接入点

现有链路已经能够接收 P6S FaceReco 事件，保存 BackgroundImage 和 CaptureImage，生成 token 图片链接，写入入场记录，并发送飞书通知。

1
摄像头发送 FaceReco 事件

事件中包含摄像头识别结果、人员信息、匹配状态，以及 BackgroundImage、CaptureImage 等图片字段。

2
服务器保存事件图片

当前已保存背景全图和人脸小图，并生成飞书可点击 token 链接。

3
新增 InsightFace 二次判断层

建议插入在图片保存之后、写入 attendance_events 和发送飞书之前。主输入使用 BackgroundImage；仅当背景图 no_face，或背景图只检测到 1 张脸但 Gallery 相似度低于 FACE_RECHECK_SIMILARITY_THRESHOLD 时，才 fallback 使用 CaptureImage。

4
根据运行模式决定是否影响业务

shadow 只记录结果；filter 可抑制低质量事件；verify_and_override 可启用二次比对纠正陌生人误判。

四、InsightFace 调研结论

事项 结论 对本项目的影响

许可证 代码 MIT；官方预训练模型默认有用途限制。用户已确认本项目可以使用 buffalo_l。 方案按 buffalo_l 设计，但模型文件和授权信息不进入仓库。

五、总体架构

P6S Camera
  |
  | FaceReco HTTP Event
  v
FastAPI Event Endpoint
  |
  | save raw event + BackgroundImage + CaptureImage
  v
InsightFace Recheck Layer
  |
  | detect face / quality gate / optional gallery match
  v
Decision Layer
  |
  | shadow: only record result
  | filter: suppress low-quality event
  | verify_and_override: correct camera stranger/known decision when confidence is high
  v
Attendance DB + Event Records + Feishu Notification

新增模块

  • FaceRecheckService：加载 InsightFace 模型并提供单张图片二次检测能力。
  • FaceQualityGate：基于检测分数、人脸尺寸、模糊度、正脸程度输出过滤结论。
  • FaceGalleryService：可选加载本地人脸 embedding 库，做二次 1:N 比对。
  • FaceRecheckDecision：把摄像头结果和服务器二次判断合并成最终业务决策。

改造原则

  • 默认失败开放：InsightFace 异常时，原摄像头链路继续工作。
  • 默认 shadow：先只记录对比结果，不直接改变通知和统计。
  • 所有阈值配置化：不把识别阈值硬编码到业务逻辑中。
  • 不把模型、图片、embedding、授权文件写入 Git。

六、运行模式设计

模式 行为 适用阶段 风险
off 不加载 InsightFace，不做二次判断。 回滚、紧急关闭。 继续依赖摄像头原始识别。
shadow 执行 InsightFace 检测和质量评估，只记录结果，不影响入场记录和主飞书通知；可额外发送到 shadow 对比机器人。 首版上线验证，建议默认。 不会减少误报，只用于收集阈值依据。
filter 对无脸、过小、模糊、侧脸、低检测分、模型异常等复核不可用事件进行抑制，不写入到场记录，不发主飞书；原始事件和处理记录仍保存。 阈值验证后启用。 这些状态不等同于“确认陌生人”，只能作为不可确认原因；阈值过严可能漏掉真实入场。
verify_and_override 在 filter 基础上，用本地人脸库二次比对。有效人脸高置信度命中时，以 InsightFace 为最终确认结果；有效人脸未高置信命中时，按陌生人处理。 人脸库 embedding 校准完成后启用。 相似阈值不准可能造成误认；本项目按“陌生人召回优先”设计，宁可误报陌生人，也不能把陌生人误放成熟人。

六补充、Shadow 对比机器人

为避免影响当前正式飞书机器人，InsightFace 的 shadow 结论使用独立机器人发送。该机器人只承载二次识别对比结果，不替代主通知、不触发入场业务动作。

消息用途

  • 展示 InsightFace 对同一条 FaceReco 事件的检测数量、检测分数、质量判断、过滤建议和二次比对结果。
  • 展示是否检测到人脸、过滤原因、选中人脸质量指标、当前阈值、Gallery 首位命中、是否通过和 Top N 候选分数，便于人工调参和验收。
  • 和主飞书机器人消息按同一个摄像头事件时间戳对齐，方便人工比较摄像头原始判断和服务器二次判断。
  • 不改变 attendance_events 是否写入，也不改变主飞书机器人是否发送。

安全与配置

  • 机器人地址和签名秘钥只写入真实环境配置，不写入 Git 跟踪文件和技术方案正文。
  • 本地配置统一写入 .env.local。
  • 远程部署时写入 /etc/camera-face-guard/app.env，并由 systemd 服务读取。

时间戳对齐规则

  • shadow 消息中的“事件时间”必须使用 P6S 事件自身的 EventTime 或当前系统已解析出的 identity.event_time。
  • shadow 消息可以额外展示“发送时间”，但不能用发送时间替代事件时间。
  • 消息中应包含 event_id、设备序列号、摄像头原始判断、InsightFace 判断和最终建议，方便和主机器人消息逐条对比。
  • 候选集最多展示 Gallery Top 5，只包含排名、姓名、身份类型、人员 ID、组名和相似度分数；不得展示 embedding 原始向量、图片 base64、webhook 或 secret。
  • 阈值展示包括检测分、最小人脸尺寸、模糊分、侧脸分、Gallery 相似度阈值和 Gallery 领先分差阈值。

消息结构优化

Shadow 机器人用于人工校验，应优先给出可读结论，而不是把底层字段平铺堆在一起。消息标题后第一段必须展示“本次最终判断”：最终动作、采信来源、主触发对象、额外触发数量和被过滤人脸数量。

  • 第一段为结论摘要，例如“最终判断：触发熟人通知；采信 InsightFace；主触发：小明 / 员工 / background:0；额外触发 1 个，过滤 2 张”。
  • 第二段展示事件基础信息，只保留事件时间、发送时间、事件 ID、设备、摄像头原始结果和摄像头人员。
  • 第三段展示 InsightFace 总览，包括状态、过滤原因、人脸数、Gallery 通过数、摄像头目标状态、冲突标记和关键阈值。
  • 逐脸结果按卡片化文本分组展示，每张脸单独列出状态、原因、质量指标、Gallery Top1、是否通过和结果对齐。
  • Gallery 候选集按每个候选单独一行展示，格式固定为“#排名 姓名 / 分组 / ID / 分数”，避免多个候选挤在同一行。

七、噪音过滤策略

过滤对象主要是摄像头误触发或低质量识别事件，不是替代全部业务判断。所有过滤原因都应写入处理记录，便于后续复盘。

语义边界：no_face、模糊、小脸、侧脸、低检测分、图片读取失败、模型异常都属于“复核不可用”，不等同于“确认陌生人”。在 filter / verify_and_override 下，这类事件可以过滤掉，不触发主飞书消息，但必须保存原始事件、处理记录、质量指标和过滤原因，供监控后台和后续日报排查。

过滤项 判断方式 默认建议 说明
无人脸 InsightFace 对 BackgroundImage 检测不到人脸；若存在 CaptureImage，先 fallback 复核人脸小图。 过滤 说明摄像头事件图片中没有可用人脸，不应触发入场提醒。
低置信度 最高人脸检测分数低于阈值。 0.55 起步，shadow 后继续校准 分数越高越保守，误报少但漏报可能增加。线上事件 713 的背景小脸检测分约 0.579，因此 0.65 会造成误过滤。
人脸过小 检测框宽高或面积占比过小。 宽高至少 80px 起步 过小人脸通常识别不稳定，容易误判。
模糊图 对人脸区域计算 Laplacian 方差。 80 起步，按真实抓拍校准 不同光照和分辨率下差异明显，必须用真实样本调阈值。
侧脸 优先使用 InsightFace 返回的姿态字段；如果字段不可用，用五点关键点几何关系估算正脸程度。 阈值校准后过滤；过滤时只记录，不触发主飞书 侧脸不应被当成熟人或确认陌生人。它是复核不可用原因，阈值需要用真实样本校准，避免侧身经过污染入场统计。
多人脸 同一背景图中检测到多张脸。 逐脸识别、逐脸决策、逐脸触发 不能再压缩成一张主脸。熟人按人员去重触发，未知有效人脸按未知人脸数量触发陌生人通知；低质量脸只记录过滤原因。

八、二次人脸库与比对策略

分阶段启用：第一阶段可以只做质量过滤；第二阶段再启用服务器侧本地人脸库二次比对。这样能先减少明显噪音，再处理摄像头把员工/会员误识别成陌生人的问题。

人脸库来源

  • 会员、教练、员工仍以已有 CSV 和图片目录作为构建来源。
  • 构建脚本读取人员 ID、姓名、分组、图片路径，生成 embedding。
  • 生成物保存到服务器私有目录，例如 /var/lib/camera-face-guard/face-gallery/gallery.npz 和 gallery_manifest.json。
  • gallery.npz 是敏感生物特征数据，不提交 Git，不通过普通部署 rsync 同步。

比对规则

  • 对通过质量过滤的人脸提取 normed_embedding。
  • 与本地 gallery embedding 做余弦相似度比对。
  • 超过 FACE_RECHECK_SIMILARITY_THRESHOLD 时，认为服务器侧高置信命中熟人；领先第二名阈值暂不作为强约束，后续出现明显 badcase 再启用。
  • 如果摄像头识别为陌生人，但服务器高置信度命中员工/会员/教练，在 verify_and_override 模式下纠正通知标题、入场类型和去重身份。
  • 如果摄像头识别为已知人员，但服务器高置信命中另一个人，在 verify_and_override 模式下信任 InsightFace，纠偏为服务器命中的人员。
  • 如果 InsightFace 有效检测到人脸但未高置信命中任何熟人，该人脸按陌生人处理；这是“确认未知人脸”，不同于 no_face、模糊、小脸、侧脸或模型异常。

八补充、最终确认逻辑

最终确认逻辑遵循“陌生人召回优先”：只有 InsightFace 对有效人脸高置信命中 Gallery 时，才按熟人处理；只要有效人脸无法高置信证明是熟人，就倾向于按陌生人提醒。复核不可用不等同于确认陌生人，可以过滤主飞书，但必须留记录。

摄像头结果 InsightFace 有效结果 最终业务动作
熟人 A 单脸，高置信命中 A 直接通过，沿用摄像头熟人流程、去重和飞书模板。
熟人 A 单脸，高置信命中 B 信任 InsightFace，纠偏为 B，按 B 的熟人流程写入和通知。
熟人 A 单脸，有效人脸但未高置信命中熟人 按陌生人处理，避免把疑似陌生人误放成熟人。
陌生人 单脸，高置信命中 A 纠偏为 A，按熟人流程写入和通知，后续去重基于 A 生效。
陌生人 单脸，有效人脸但未高置信命中熟人 保持陌生人流程。
任意 多张有效脸 逐脸决策：高置信命中熟人的脸按熟人触发；未高置信命中的有效脸按陌生人逐张触发；同一人员在同一事件内去重。
任意 no_face / 模糊 / 小脸 / 侧脸 / 模型异常 复核不可用。可以过滤主飞书，不写入 attendance_events，但必须保存处理记录和原因；不得把它当作确认陌生人。

该逻辑必须插入在图片保存和 InsightFace 复核之后、attendance_events 写入和主飞书通知之前，否则无法正确影响通知去重。

低质量未知分层

陌生人提醒必须进一步拆分为“确认陌生人”和“低质量未知”。低质量未知不是熟人，也不是确认陌生人；它代表当前单帧无法可靠判断身份，只写处理记录和监控后台，不触发主飞书陌生人提醒。

  • 本期实现：新增 face_near_border、motion_blur、low_identity_confidence 三类降噪信号。
  • 确认陌生人：质量可用、未贴边、未运动模糊，即使 Gallery Top1 分数低，也可以按陌生人触发，避免漏掉真正陌生人。
  • 低质量未知：未高置信命中熟人，且存在贴边裁切或运动模糊；低身份置信度用于增强解释和辅助过滤，但不能单独作为所有陌生人过滤条件。
  • 暂不实现：不启用 unknown_face_too_small，避免小脸线索被过早过滤；不做 3-5 秒短窗口聚合，避免引入状态管理复杂度。

九、配置设计

所有真实配置继续写入服务器环境文件；本地真实配置写入 .env.local。不新增 .env.local2 等临时配置文件。

FACE_RECHECK_MIN_FACE_HEIGHT 80 最小人脸高度。
FACE_RECHECK_BLUR_THRESHOLD 80 模糊过滤阈值，基于人脸区域 Laplacian 方差。
FACE_RECHECK_HEAD_PITCH_MIN -45 低头/头顶过滤阈值，基于 InsightFace pose[0] pitch；小于该值标记为 head_pitch_bad。
FACE_RECHECK_SIMILARITY_THRESHOLD 0.50 起步 服务器侧 gallery 命中的相似度阈值，需要用真实样本校准。
FACE_RECHECK_GALLERY_PATH /var/lib/camera-face-guard/face-gallery/gallery.npz 本地 embedding 库路径，仅 verify_and_override 需要。
FACE_RECHECK_FAIL_OPEN true InsightFace 异常时是否继续原始摄像头链路。建议保持 true。

十、部署方案

本地验证

  1. 在本地虚拟环境安装 insightface==1.0.1、onnxruntime、opencv-python-headless、numpy。
  2. 使用已解压的本地模型目录 /Users/congming/.insightface/models/buffalo_l。本地代码可以使用默认 root="~/.insightface"，也可以显式配置 INSIGHTFACE_MODEL_ROOT=/Users/congming/.insightface。
  3. 选取真实事件中保存的 BackgroundImage 样本，跑检测、模糊度、正脸判断和耗时统计；同时验证背景图失败或低相似度时的 CaptureImage fallback 行为。
  4. 先生成 shadow 报告，不接入生产飞书。

远程部署

  1. 在 qypower-prod 创建模型目录：/var/lib/camera-face-guard/insightface/models/buffalo_l。
  2. 从本地已验证目录上传模型文件到远程，例如将 /Users/congming/.insightface/models/buffalo_l/ 同步到 qypower-prod:/var/lib/camera-face-guard/insightface/models/buffalo_l/。
  3. 模型文件由人工或专用脚本上传，权限归属 ubuntu，不进入应用 Git 仓库，也不通过普通应用 rsync 发布。
  4. 更新 requirements.txt 后，通过现有部署脚本安装依赖。
  5. 在 /etc/camera-face-guard/app.env 增加 InsightFace 配置，初始使用 FACE_RECHECK_MODE=shadow。
  6. 重启 camera-face-guard，验证服务启动、事件接收、shadow 记录和飞书原行为不变。
  7. 收集足够真实样本后，再切换到 filter 或 verify_and_override。

CPU 约束：当前远程服务器是 2 核 CPU、约 7.5Gi 内存、无 GPU。事件触发式二次识别可行，但 RTSP 连续帧识别暂不建议部署在这台机器上。

十一、影响面

模块 影响 控制方式
事件接收 不改变 API endpoint 和摄像头推送格式。 只在服务内部新增二次判断。
图片保存 继续保存 BackgroundImage 和 CaptureImage。 InsightFace 使用已保存的背景全图，不改变双图链接。
入场记录 shadow 不影响；filter 会让低质量事件不进入到场统计。 切换模式前必须用样本验证过滤准确率。
飞书通知 shadow 不影响；filter 会抑制低质量通知；verify_and_override 可能改变陌生人/已知人员标题。 所有决策写入处理记录，便于追溯。
性能 每条事件增加 CPU 推理耗时。 模型单例加载、限制并发、设置超时、失败开放。
部署 新增 Python 依赖和模型文件。 模型独立存放，部署脚本校验，不提交 Git。

十二、风险点与应对

误过滤真实入场

侧脸、模糊、低分阈值设置过严，会漏掉真实人员。应对：首版 shadow，用真实样本调参后再启用 filter。

CPU 延迟

buffalo_l 准确率较高但模型较大。应对：事件触发式处理、模型单例、超时失败开放；如延迟不可接受，再评估 buffalo_s 或更高配置服务器。

二次误认

相似度阈值过低可能把陌生人误认为会员/员工。应对：二次比对必须先 shadow，启用时要求最高分超过熟人阈值；领先第二名暂不作为强约束，后续出现明显 badcase 再启用。

模型文件缺失

生产运行时自动下载模型不可控。应对：模型预置到私有目录，启动时校验，缺失则记录错误并按 fail-open 继续原链路。

敏感数据泄露

人脸图片、embedding、模型授权信息都属于敏感资产。应对：不提交 Git，部署脚本排除，服务器目录限制权限。

调试不可追溯

如果只抑制通知不记录原因，后续无法判断是否误杀。应对：原始事件继续保存，recheck 结果写入处理记录。

十三、回滚方式

  1. 优先回滚：将 FACE_RECHECK_ENABLED=false 或 FACE_RECHECK_MODE=off，重启服务。
  2. 如果依赖引发启动异常：回滚到上一版代码或临时移除 InsightFace 依赖，服务恢复原 P6S 事件链路。
  3. 如果模型文件异常：删除或移动模型目录不会影响原链路，因为服务应 fail-open。
  4. 如果二次比对误认：切回 shadow 或 filter，保留质量过滤，关闭身份覆盖。
  5. 本方案不修改摄像头配置，因此不需要摄像头侧回滚。

十四、验证方式

本地验证

  • 使用真实 BackgroundImage 样本验证：正脸会员、正脸员工、陌生人、侧脸、模糊图、无人脸、多人大图。
  • 输出每张图片的检测数量、最高检测分、bbox、脸宽高、模糊度、正脸判断、耗时和最终决策。
  • 对同一批样本重复运行，确认结果稳定。

服务验证

  • FACE_RECHECK_MODE=shadow 时，飞书消息和入场记录与当前行为一致，只新增 recheck 记录。
  • FACE_RECHECK_MODE=filter 时，低质量事件不发飞书、不写到场统计，但原始事件和过滤原因可查。
  • FACE_RECHECK_MODE=verify_and_override 时，摄像头陌生人但服务器高置信度命中员工/会员/教练的事件，按服务器识别结果发通知。
  • InsightFace 初始化失败、模型缺失、图片解码失败、推理超时等异常场景均不应导致事件接口 500。

性能验证

  • 记录单张图推理耗时，关注 p50、p95。
  • 验证连续多条事件时服务不会阻塞摄像头推送。
  • 如果 CPU 持续过高，优先降低并发或切回 shadow/off，不直接切 RTSP 自研识别。

十五、实施顺序

  1. 评审本技术方案，确认运行模式、默认阈值、过滤是否影响入场统计。
  2. 编写 LLD，细化模块边界、函数签名、配置读取、异常处理、测试夹具和部署命令。
  3. 本地写一个离线 POC 脚本，对真实事件图片生成 recheck 报告。
  4. 开发服务内 InsightFace shadow 模式，不改变现有业务结果。
  5. 部署到远程并运行 shadow 模式，收集至少一批真实事件样本。
  6. 根据样本调整阈值，再决定是否开启 filter。
  7. 构建服务器侧 gallery embedding，校准相似度阈值后，再决定是否开启 verify_and_override。

十六、837/838 误判修复方案

线上事件 837 和 838 暴露出两个边界问题：摄像头已识别到熟人时，InsightFace 不应因为 Capture 小图轻微低于尺寸阈值就丢弃同人证据；当 Gallery Top1 与摄像头人员候选分差极小时，也不应贸然纠偏成另一个人。

修复点 规则 目标效果
摄像头同人候选保护 当摄像头为 known，且 Gallery Top5 中存在与摄像头姓名或 ID 一致的候选，该候选相似度达到 FACE_RECHECK_CAMERA_MATCH_SIMILARITY_THRESHOLD，并且与 Top1 分差不超过 FACE_RECHECK_CAMERA_MATCH_GAP_THRESHOLD 时，优先选择摄像头同人候选。 避免 838 这种 Top1/Top2 只差约 0.002 时错误覆盖成另一个熟人。
Capture 目标脸救援 当摄像头为 known，Capture 图中与摄像头人员一致的 Gallery 命中达到同人阈值，且只因 face_too_small 被过滤、没有侧脸/模糊/低检测分时，可用较低的救援尺寸阈值放行。 避免 837 这种正确 Capture 小脸被尺寸阈值一刀切过滤。
额外陌生脸门控 当摄像头已识别 known 且同一事件已找到摄像头目标脸时，其他未命中 Gallery 的额外人脸必须满足更高的陌生人触发尺寸阈值，才按陌生人通知。 减少目标熟人旁边的小脸、弱脸被误报为陌生人；真正清晰的大陌生脸仍会触发。
  • 范围：只修改服务器侧 InsightFace Gallery 匹配和最终确认逻辑，不修改摄像头配置、摄像头脸库、飞书模板、数据库 schema 或监控 UI。
  • 风险：同人候选保护依赖摄像头姓名/ID 的正确性，只在 Top5 分差很小时生效；额外陌生脸门控可能降低已知人员同框小陌生脸的提醒概率，但符合“低质小脸先不误报”的当前调参目标。
  • 回滚：最快可将 FACE_RECHECK_MODE 切回 shadow 或 FACE_RECHECK_ENABLED=false；代码层面可回滚本次提交。
  • 验证：本地 fixture 覆盖 Top1/Top2 极近同人保护、Capture 小图同人救援、已知人员场景额外小陌生脸抑制、侧脸/模糊仍过滤；部署后重点复查事件 837、838 同类行为。

十七、Gallery 增量同步方案

Gallery 是由本地 P6S 命名图片目录构建出的运行时资产。新增会员、员工或教练时，不直接手工编辑 gallery_manifest.json 或 gallery.npz，而是以源目录为准重新构建完整 Gallery，验证后替换远程资产。

输入 用途 同步规则

styd_member_faces_p6s_named 会员小图一致性检查。 新增会员建议同时存在小图，便于和摄像头人脸库/人工核对一致；构建 Gallery 时仍使用大图。
staff_p6s_named 员工 Gallery embedding 构建源。 按目录注入 person_type=staff。
teacher_p6s_named 教练 Gallery embedding 构建源。 按目录注入 person_type=coach。
  • 本次新增：Immm#S0#T2#M2646107121905699.jpg 已存在于会员大图和小图 P6S 命名目录，预期远程 Gallery 从 264 条增至 265 条。
  • 验证：构建前后需要比对本地源目录与远程 manifest，确认新增人员 ID 出现在 person_type=member 且 name=mmm。

  • 复用：将本流程沉淀为 Codex 技能“增加会员信息到gallery”，后续触发时自动做目录比对、构建、上传和验证。

十八、新增人员类型：上课会员

上课会员是“只上课但尚未注册为正式会员”的人员类型，应与会员、教练、员工同级管理。该类型进入服务器侧 InsightFace Gallery 后，可以把摄像头识别为陌生人的事件纠正为“上课会员”，从而避免把已知上课人员误报为陌生人。

目标

  • 新增业务展示名 上课会员，内部类型建议为 class_member。
  • Gallery 构建源新增上课会员 P6S 命名图片目录，当前本地目录为 unregister_class_member。
  • 本次样本 I杜全浩紫发会员#S0#T2#M2026070501.png 已通过质量预检：单人脸、正脸、检测分 0.848676、尺寸 106.8x145.725、无质量过滤标记。
  • verify_and_override 模式下，如果摄像头识别为陌生人但 InsightFace 高置信命中上课会员，应按上课会员触发主飞书和入场记录。

范围

模块 需要调整 说明
Gallery 构建 新增 class_member 来源目录。 按目录注入 person_type=class_member、group_name=上课会员；仍从 P6S 文件名解析姓名、性别、证件类型和 ID。
Gallery 匹配 扩展允许的人员类型。 GalleryCandidate、GalleryMatch、manifest 校验和 Top5 展示都要支持 class_member。
最终确认逻辑 把上课会员作为熟人类型处理。 高置信命中时触发熟人通知；低分或质量不可用仍按现有陌生人召回和过滤规则执行。
主飞书 新增标题和身份文案。 建议标题为 📚 上课会员入场提醒；正文保留姓名、身份类型、时间、事件 ID 和图片链接。
入场记录与日报 新增人员类型统计。 attendance_events.person_type 需要允许 class_member；日报建议新增 class_member_entries，避免混入正式会员统计。
监控后台 展示新类型。 列表筛选、详情身份标签、Gallery 候选集和最终结论都要展示“上课会员”。
本地资产 保持私有目录不进 Git。 unregister_class_member/ 或后续规范目录都必须被 .gitignore 忽略，只提交代码和文档，不提交人脸图片。

不做事项

  • 不把上课会员写入摄像头人脸库，不创建摄像头脸库分组，不修改摄像头配置。
  • 不把上课会员归入正式会员 member，避免污染会员入场统计和提醒去重。
  • 不提交真实人脸图片、Gallery embedding、manifest 或远程运行时资产。

数据与命名规则

  • 图片命名继续使用 I名称#S性别#T证件类型#M证件号码.jpg/png。
  • 样本姓名为 杜全浩紫发会员，人员 ID 为 2026070501。
  • Gallery 内部唯一键仍为 person_type + person_id，所以上课会员可以和正式会员使用相同 ID 空间但不会互相覆盖；实际录入时仍建议 ID 全局唯一，便于人工排查。

风险点

  • 当前代码多处使用 Literal["member", "coach", "staff"] 和数据库 check 约束，新增类型必须整体扩展，不能只改 Gallery 构建脚本。
  • 日报字段如果写死为会员、教练、员工、陌生人，新增类型后需要同步调整统计 SQL 和飞书日报文案。
  • 上课会员和正式会员都属于“熟人”，需要沿用 2 小时去重逻辑；否则同一上课会员多次识别会重复提醒。
  • 上课会员来自人工维护目录，命名错误或重复 ID 会直接影响 Gallery 匹配结果，构建报告必须阻断重复 person_type + person_id。

回滚方式

  • 最快运行时回滚：从 Gallery 资产中移除上课会员记录或恢复旧版 Gallery，并重启服务。
  • 代码回滚：回滚新增 class_member 支持的提交，并执行对应 Alembic downgrade 或兼容迁移。
  • 业务降级：临时将 FACE_RECHECK_MODE 切回 shadow，只观察上课会员命中，不影响主飞书和入场记录。

验证方式

  • 本地 Gallery 构建预检：确认 unregister_class_member 中 P6S 命名图片可解析，重复 ID 为 0，InsightFace 检测为单人脸且质量通过。
  • 本地 fixture：覆盖摄像头陌生人但 Gallery 命中上课会员，最终决策应为熟人触发，标题应为 📚 上课会员入场提醒。
  • DB 验证：attendance_events.person_type=class_member 可写入，去重窗口与会员/教练/员工一致。
  • 监控验证：识别详情、逐脸 Gallery 候选、最终结论和筛选项都能显示“上课会员”。
  • 远程部署验证：备份旧 Gallery，上传新 Gallery 后确认 manifest 中出现 person_type=class_member、name=杜全浩紫发会员、person_id=2026070501。

十九、已拍板结论

问题 已确认结论 执行要求
首版上线模式 shadow 只发送 InsightFace shadow 对比机器人消息，不影响主飞书、不影响入场记录和日报统计。
过滤后是否写入入场记录 filter 模式下不写入 attendance_events。 只保留原始事件和处理记录，避免侧脸、模糊、无人脸污染日报。后续如果需要统计本地模型拦截数量和原因，应基于处理记录中的 face_recheck.reason 单独统计。
已知人员与服务器比对冲突时如何处理 在 verify_and_override 模式下信任 InsightFace。 如果 InsightFace 对有效人脸高置信命中 B，而摄像头识别为 A，则纠偏为 B。若 InsightFace 结果属于复核不可用，则不推翻摄像头结果，只记录原因。
摄像头陌生人但服务器高置信命中时如何处理 verify_and_override 模式下允许纠正为会员/教练/员工。 必须满足 gallery 相似度超过阈值，才允许覆盖摄像头陌生人结果。领先第二名阈值暂不强制，后续出现明显 badcase 再启用。
陌生人召回优先 熟人必须高置信确认；有效人脸未高置信命中熟人时，倾向按陌生人提醒。 不能把低分熟人命中当成熟人放行。多人脸中每张有效未知脸都按陌生人数量触发通知。
复核不可用语义 no_face、模糊、小脸、侧脸、低检测分、图片/模型异常不等同于确认陌生人。 这些状态可以过滤主飞书和 attendance_events，但必须保存原始事件、处理记录、质量指标和过滤原因。
是否做 RTSP 全量识别 本期不做。 当前服务器 CPU 资源有限，且事件触发式方案已能覆盖主要问题。
Gallery 构建失败策略 单人失败不阻断全量构建。 失败人员必须写入 build_report；如果小明等关键测试人员失败，需要停下来修正图片后再继续。
其他默认项 按本方案和 LLD 默认建议执行。 包括 CPU-only、buffalo_l、模型不进 Git、embedding 不进 Git、默认 fail-open、侧脸阈值先用真实样本校准后再作为过滤条件。

P6S InsightFace 多人脸逐脸识别 LLD

基于《P6S InsightFace 多人脸逐脸识别技术方案》，细化数据库、服务、事件记录、监控 API、页面展示、回填和验证步骤。

事件父表保持 recognition_events 新增 recognition_event_faces shadow-only 首版 Alembic 管理迁移

一、模块边界

模块/文件 职责变化
app/services/face_recheck.py 从“单个 selected_face”升级为“保留事件级摘要 + 输出逐脸结果列表”。继续提供兼容字段 selected_face / gallery_match，但新增 faces 作为权威逐脸结果。
app/services/face_gallery.py 保持现有 Gallery 加载和 match 能力；由 face_recheck.py 对每张 face embedding 调用一次。
app/services/p6s_events.py 事件处理流保持不变，仍在图片保存后调用 run_face_recheck()；写 processing record 时保存 face_recheck.faces。
app/services/recognition_monitor.py 从 processing record 构建父表 row 和子表 face rows；提供监控 DTO、crop 生成和详情聚合。
app/db/recognition_repo.py 新增 upsert_recognition_event_faces()、list_recognition_event_faces()、delete_stale_faces_for_event() 等数据库函数。
alembic/versions/*_create_recognition_event_faces.py 新增子表、唯一约束、外键和查询索引。
scripts/backfill_recognition_events.py 扩展为可回填子表；历史记录缺少 face_recheck.faces 时可选择重新运行多脸 recheck。

四、识别流程

def run_face_recheck(input, settings):
    background_faces = analyze_image_faces(
        image_path=input.background_image_path,
        image_source="background",
    )

    capture_faces = []
    if should_analyze_capture(input, background_faces):
        capture_faces = analyze_image_faces(
            image_path=input.capture_image_path,
            image_source="capture",
        )

    all_faces = background_faces + capture_faces
    primary = choose_primary_face_for_compatibility(all_faces, input.camera_person)
    return build_event_result(all_faces, primary)

def analyze_image_faces(image_path, image_source):
    faces = app.get(image)
    results = []
    for index, face in enumerate(faces):
        summary = summarize_face(index, face)
        status, reason = evaluate_quality(summary)
        gallery_match = gallery.match(face.normed_embedding)
        results.append(FaceRecheckFaceResult(...))
    return results

CaptureImage 触发规则

  • 背景图无脸：处理 Capture 图。
  • 背景图有多脸且摄像头结果是 known：处理 Capture 图作为摄像头目标脸辅助证据。
  • 背景图单脸但 Gallery 相似度低于阈值：沿用当前 fallback 规则处理 Capture 图。
  • Capture 图结果不覆盖背景图结果，只作为额外 image_source=capture 行保存。

事件级 primary_face 兼容选择

为了兼容现有 shadow 消息和列表摘要，仍需要一个 primary face，但它只用于摘要，不代表全部结果。

  1. 如果存在 accepted=true 且与摄像头 known 姓名/ID 对齐的人脸，优先选它。
  2. 否则选 accepted=true 且相似度最高的人脸。
  3. 否则选 Gallery Top1 与摄像头姓名一致的人脸，即使未过阈值。
  4. 否则退回当前 面积 x 检测分 最大的人脸。

五、数据库写入流程

5.1 实时写入

def safe_upsert_processing_record_file(record_path):
    record = read_json(record_path)
    event_row = build_event_row(record)
    face_rows = build_event_face_rows(record)
    with transaction() as conn:
        event = upsert_recognition_event(conn, event_row)
        upsert_recognition_event_faces(
            conn,
            recognition_event_id=event["recognition_event_id"],
            rows=face_rows,
        )
        delete_stale_faces_for_event(
            conn,
            recognition_event_id=event["recognition_event_id"],
            keep_keys=[row["face_key"] for row in face_rows],
        )

5.2 Upsert 规则

  • 父表唯一键仍为 event_dedupe_key。
  • 子表唯一键为 recognition_event_id + image_source + face_index。
  • 同一事件重刷后，如果脸数变少，删除本事件下不再存在的旧 face rows。
  • 处理记录中没有 faces 时，子表写入为空；历史回填脚本可选择重新运行 recheck 生成。

八、回填与重刷

脚本参数

python3 scripts/backfill_recognition_events.py \
  --date 2026-07-04 \
  --apply \
  --recheck-missing-faces

行为

  • 默认读取 processing record 中已有 face_recheck.faces。
  • 如果缺少 faces 且指定 --recheck-missing-faces，则用当前线上模型和 Gallery 重新跑多脸识别。
  • 回填写入父表和子表，但不发飞书、不写 attendance、不触发去重、不改摄像头。
  • 运行报告输出处理数、父表 upsert 数、子表 upsert 数、删除旧 face 数、错误列表。

十一、部署步骤

  1. 新增 Alembic 迁移，创建 recognition_event_faces 和父表摘要字段。
  2. 本地执行 python3 -m py_compile 和 fixture 验证。
  3. 部署代码到 qypower-prod，执行 alembic upgrade head。
  4. 先对 7 月 4 日执行 dry-run 回填，确认事件数和 face rows 数。
  5. 执行 apply 回填，打开监控后台验证事件 672。
  6. 观察实时事件是否持续写入父表和子表。
部署和验证不得写摄像头配置，不得修改脸库，不得切换 InsightFace 模式到 filter 或 verify_and_override。

十二、回滚方式

  • 应用回滚：回滚服务代码到上一提交，父表旧逻辑仍可运行。
  • 数据库回滚：新增子表不影响旧功能；若必须回滚，可执行 Alembic downgrade 删除子表和新增摘要字段。
  • 运行回滚：如果子表写入异常，临时关闭子表 upsert，只保留父表写入和原 processing record。

十二补充、filter / verify 最终确认约束

本 LLD 的数据结构必须支持后续最终确认逻辑。当前多人脸落库仍可保持 shadow 行为，但字段设计和回填结果要能解释每张脸后续是否会触发主飞书。

逐脸状态 业务含义 落库与页面要求
IF-K 有效人脸且 Gallery 高置信命中熟人。 子表保留命中人员、角色、相似度、Top5、business_action=known_trigger。
IF-U 有效人脸但 Gallery 未高置信命中熟人；按陌生人召回优先原则，需要触发陌生人。 子表保留质量分、bbox、crop、business_action=stranger_trigger，页面展示为有效未知脸。
IF-NA no_face、模糊、小脸、侧脸、低检测分、图片读取失败、模型异常；复核不可用，不等同于确认陌生人。 子表或父记录必须保留 business_action=suppressed、suppress_reason、质量指标；页面展示“已过滤，不触发主飞书”。
  • 多人脸事件逐脸触发：多个有效未知脸按未知人脸数量触发陌生人通知。
  • 摄像头 known 与 InsightFace 高置信命中其他熟人冲突时，后续 verify_and_override 以 InsightFace 为准。
  • 但当摄像头 known 的同人候选已经出现在 Gallery Top5，且与 Top1 分差极小，应优先保留摄像头同人候选，避免近似并列候选误纠偏成其他熟人。
  • 摄像头 known 的 Capture 图如果命中摄像头同人，只能在仅有 face_too_small 且满足救援尺寸时放行；side_face、blurred、low_det_score 仍然必须过滤。
  • 摄像头 known 且已确认目标脸时，其他未命中 Gallery 的额外未知脸需要满足更严格的额外陌生脸尺寸门槛，否则只记录 suppress_reason=extra_unknown_too_small_for_known_event。
  • 同一事件中同一熟人跨 background / capture 重复出现时，按 person_type + person_id 去重。
  • 最终确认必须发生在主链路写 attendance_events 和发送主飞书之前；监控表只负责记录和展示，不反向驱动主流程。

十三、待确认项

事项 建议默认值
父表是否增加 accepted_face_count 等摘要字段 建议增加，便于列表筛选和减少详情 join。
背景图多脸时是否总是处理 Capture 图 建议仅在摄像头结果为 known 时处理 Capture 图，作为目标脸辅助证据。
事件级 primary face 是否继续保留 建议保留兼容字段，但 UI 和分析以 faces 为准。

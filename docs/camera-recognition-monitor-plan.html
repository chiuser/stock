Recognition Monitor · Plan

P6S 摄像头识别监控后台

本方案把当前“一次性离线回放报告”升级为长期可用的识别质量监控后台。后台用于持续查看 P6S 摄像头原始识别、InsightFace + Gallery 二次识别、过滤原因、候选集分数和图片证据，帮助快速判断“谁识别对了、谁识别错了、哪些事件应该被过滤”。

一、目标与边界

核心目标

  • 提供一个网页页面，实时查看摄像头事件与 InsightFace 复核结果。
  • 每条记录同时展示摄像头判断、InsightFace 判断、Gallery Top 候选、分数和过滤原因。
  • 支持按识别一致、摄像头漏识别、疑似错误、低质量过滤、陌生人、人员姓名、日期等维度筛选。
  • 能直接查看背景全图、人脸小图和模型选中人脸区域，方便人工判断识别是否靠谱。

本期不做

  • 不修改摄像头配置、不修改人脸库、不改变 P6S 事件推送方式。
  • 不启用 filter 或 verify_and_override 的业务干预。
  • 不替代主飞书通知和日报，只作为识别质量监控页面，不做人工复核写入。
  • 不把 embedding、密钥、webhook、图片 base64 暴露到前端或报告。

二、现有能力与推荐路线

当前服务已经保存了每条 FaceReco 的处理记录，记录里包含 matched_person、images.background、images.capture、links 和 face_recheck。但监控后台是长期产品能力，V1 直接建立 PostgreSQL 识别监控索引表，并用回填脚本把历史 JSON 写入数据库，避免后续再做二次迁移。

V1 推荐

PostgreSQL 索引表

事件处理时把安全摘要写入 recognition_events；历史记录通过 backfill 脚本从 records/YYYY-MM-DD/*.json 补写。查询、筛选、分页都走数据库。

增强

实时轮询

前端每 10 秒请求最新事件。因为 P6S 推送频率不高，轮询足够稳定，不需要首版引入 WebSocket。

四、后台接口设计

接口 用途 关键参数 返回重点
GET /recognition-monitor 识别监控后台页面。 依赖管理员登录态。 已登录返回静态 HTML 页面；未登录进入登录页或由前端跳转登录页。
GET /api/recognition-monitor/summary 顶部统计卡片和分类数量。 date 总数、摄像头已识别、陌生人、模型 accepted、疑似冲突、各过滤原因数量。
GET /api/recognition-monitor/events 分页事件列表。 date、classification、person、reason、page、page_size 事件时间、事件 ID、摄像头结果、InsightFace 结果、分类、分数、图片链接摘要。
GET /api/recognition-monitor/events/{event_id} 事件详情弹层。 event_id 或记录 dedupe_key 完整 recheck、Gallery Top 5、阈值、质量 flags、原始记录安全摘要。
GET /api/p6s/event-images/view/{token} 复用现有 token 图片查看接口。 token 背景全图、人脸图；不新增裸路径访问。

如果历史记录缺少图片 token，接口可基于已有 relative_path 生成短期只读 token；生成 token 只用于查看图片，不改变识别业务结果。

五、分类规则

分类 判断条件 页面含义
same_person 摄像头识别为已知人，InsightFace accepted，姓名或 ID 对齐。 基本可信，可抽样复核。
camera_missed_but_gallery_hit 摄像头识别为陌生人，InsightFace accepted 某个 Gallery 人员。 重点查看，通常代表摄像头漏识别或角度问题。
camera_hit_but_recheck_filtered 摄像头识别为已知人，但 InsightFace 结果 filtered 或 no_face。 用于判断是否应在 filter 阶段拦截低质量事件。
identity_conflict InsightFace accepted 且与摄像头已知人员身份不一致。 最高优先级，疑似误识别或 Gallery 数据问题。
both_unknown_or_filtered 摄像头陌生人且 InsightFace 未 accepted，或双方都没有可靠身份。 通常是陌生人、侧脸、小脸、多人或无脸噪音。

六、数据流

  1. P6S 摄像头推送 FaceReco 事件到服务器。
  2. 现有事件处理保存 raw、processing record、背景图、人脸图和 token 链接；已拍板监控后台展示图片时改走管理员鉴权图片代理 + 前端 fetch blob。
  3. 现有 InsightFace shadow 链路生成 face_recheck 结果。
  4. InsightFace 检测到人脸时，使用背景图和 bbox 生成服务器侧人脸裁剪图，用于和摄像头 CaptureImage 对比。
  5. 事件处理完成后，将摄像头结果、InsightFace 结果、图片相对路径和分类摘要 upsert 到 recognition_events。
  6. 监控后台 API 查询 PostgreSQL 表，完成筛选、排序、分页和统计。
  7. 前端页面轮询 summary 和 events 接口，并通过管理员鉴权图片代理 + 前端 fetch blob 查看图片。

对于老记录中缺失 face_recheck 的情况，回填脚本写入 not_rechecked 状态；是否补跑离线 recheck 由单独脚本完成，不在页面请求中临时跑模型，避免接口变慢。

七、实现分阶段

Milestone 1：只读监控页面

  • 新增 recognition_events 表、回填脚本、监控页面和只读 API。
  • 实时事件处理时 upsert 识别监控摘要，页面查询数据库展示颜色分类、筛选、图片缩略图和详情弹层。
  • 页面展示所有 FaceReco：缺图或未复核显示占位状态，不从列表中隐藏。
  • 前端每 10 秒自动刷新，不引入 WebSocket。
  • 背景图先显示缩略图，点击后弹窗展示大图；弹窗同时展示摄像头 CaptureImage 和 InsightFace 裁剪图。

Milestone 2：识别质量分析

  • 基于 recognition_events 统计按天趋势、过滤原因和摄像头/InsightFace 差异。
  • 增加阈值调参观察视图，但不在本期做人工复核写入。
  • 需要导出时只导出安全摘要，不导出图片正文或 embedding。

Milestone 3：效果看板

  • 按天统计摄像头漏识别、模型过滤、冲突、同人确认趋势。
  • 提供阈值调参参考，例如小脸过滤后仍 accepted 的比例。
  • 为后续启用 filter 提供数据依据。

Milestone 4：索引与性能

  • 根据查询量补充复合索引、归档策略或按日汇总表。
  • 避免接口直接扫描文件系统。
  • 保留原始 JSON 作为审计来源。

八、风险与验证

风险控制

  • 页面和 API 必须走管理员登录鉴权。
  • 监控后台需要登录页面：优先复用现有登录页和 JWT；如果当前服务没有可用登录页，本需求内补一个最小管理员登录页。
  • 不得返回 webhook、secret、Owner、摄像头密码、embedding、图片 base64。
  • 默认只读取已有记录，不在请求链路中跑重模型。
  • 已拍板图片通过管理员鉴权代理 + 前端 fetch blob 读取，不暴露服务器真实文件路径给普通页面。

验收方式

  • 打开页面能看到当天事件总览和颜色分类数量。
  • 能筛选出 camera_missed_but_gallery_hit 的 4 条历史样本。
  • 能查看每条记录的背景全图、人脸图、摄像头结果和 InsightFace Top 5。
  • 页面刷新后新事件自动出现在列表中，且不影响主飞书和入场记录。

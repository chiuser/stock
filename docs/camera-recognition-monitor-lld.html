Recognition Monitor · LLD

P6S 摄像头识别监控后台代码级设计

本 LLD 基于 docs/camera-recognition-monitor-plan.html 细化到模块、接口、数据库表结构、回填脚本、前端交互和验证步骤。目标是交付一个长期可用的识别监控后台，让管理员持续查看摄像头识别和 InsightFace + Gallery 识别结果，并快速判断识别是否正确。

一、设计基线与性能结论

对远程 qypower-prod 做过只读容量统计，当前 records 文件很小，图片和 raw 事件才是主要体积来源。从性能上看短期扫描 JSON 可行，但该后台是长期产品能力，V1 直接建立 PostgreSQL 索引表，并通过 Alembic 管理表结构，避免后续历史数据二次迁移。

日期 JSON 数 records 大小 FaceReco 有背景图 解析耗时
2026-07-02 451 0.17MB 2 0 约 9.84ms
2026-07-03 2960 1.52MB 264 0 约 69.15ms
2026-07-04 2786 1.88MB 440 38 约 63.60ms

LLD 结论：Milestone 1 直接使用 recognition_events PostgreSQL 表。历史 records/YYYY-MM-DD/*.json 通过 backfill 脚本补写入库；后续实时事件在处理完成后 upsert 监控摘要。原始 JSON 继续保留为审计事实源。

二、模块边界

模块 职责 边界
app/services/recognition_monitor.py 把处理记录和 recheck 结果转换成监控 DTO，派生分类，提供安全字段清洗。 不发飞书、不跑 InsightFace 重模型、不直接操作 HTTP。
app/db/recognition_repo.py 写入和查询 recognition_events，提供 summary、分页、详情查询。 只存安全摘要和图片相对路径，不存 embedding、base64、密钥或绝对路径。
alembic/versions/*_create_recognition_events.py 创建识别监控索引表和必要索引。 由 Alembic 管理，不手写生产 SQL。
scripts/backfill_recognition_events.py 从历史 records/YYYY-MM-DD/*.json 回填识别监控表。 只读事件 JSON，只写 recognition_events；支持 dry-run 和日期范围。
app/routers/recognition_monitor.py 提供监控后台 API 和管理员鉴权图片代理。 所有接口依赖 require_admin；不暴露绝对文件路径和密钥。
app/static/recognition-monitor.html 识别监控页面结构。 复用当前登录态，导航中加入“识别监控”。
app/static/recognition-monitor.js 筛选、分页、轮询、图片 blob 加载、详情弹层。 不直接访问裸图片 URL；通过带 Authorization 的 fetch 获取图片 blob。
app/main.py 注册页面路由和 API router。 新增 /recognition-monitor 页面，不改变现有 /camera。

三、数据模型

数据库表：recognition_events

V1 建一张识别监控索引表，数据来源是实时事件处理结果和历史 processing record 回填。表中只保存监控页面需要查询和展示的安全摘要，原始 JSON 和图片文件继续留在事件目录中。

写入策略：实时事件处理完成后按 event_dedupe_key upsert；历史数据由 backfill 脚本按日期范围读取 JSON 后 upsert。这样脚本可重复执行，不会产生重复记录。

前端 DTO

服务层统一把原始处理记录转换成前端安全 DTO。DTO 不包含 webhook、secret、Owner、摄像头密码、embedding、图片 base64 或服务器绝对路径。

数据来源映射

DTO 字段 来源 处理规则
摄像头结果 recognition_events.camera_result、camera_person_* 已知人员展示姓名、ID、角色；陌生人展示“陌生人”。
InsightFace 结果 recognition_events.recheck_*、gallery_* 缺失时统一展示 not_rechecked，不在 API 请求中补跑模型。
图片 background_relative_path、capture_relative_path、insightface_crop_relative_path 只保留 relative path、content type 和 API URL，不返回绝对路径；InsightFace 裁剪图由背景图和 bbox 生成。
分类 classification 实时写入和 backfill 时由服务层纯函数派生，前端只展示，不重新判断。

四、分类规则

分类 条件 优先级 颜色
identity_conflict gallery_accepted=true 且摄像头已知人员与 Gallery 身份不一致。 最高 红
camera_missed_but_gallery_hit 摄像头为陌生人或未知，且 gallery_accepted=true。 高 黄
same_person 摄像头已知人员，gallery_accepted=true，且姓名或 ID 对齐。 中 绿
camera_hit_but_recheck_filtered 摄像头已知人员，但 recheck 为 filtered、no_face 或未 accepted。 中 橙
not_rechecked 历史记录缺失 face_recheck。 低 蓝
both_unknown_or_filtered 双方都没有可靠身份，或陌生人低质量过滤。 低 蓝

注意：低分候选即使和摄像头身份不同，也不能算 identity_conflict。只有 Gallery accepted=true 后才进入冲突判断，避免把“低分 Top1 候选”误判成模型错误。

五、数据库写入与回填策略

V1 所有监控查询都走 recognition_events 表。文件系统只作为历史回填和审计来源，不作为页面 API 的实时查询路径。

实时写入

  • 在 app/services/p6s_events.py 写完 processing record 后，调用 recognition_monitor.safe_upsert_processing_record_file(record_path)。
  • 如果背景图存在且 InsightFace 返回选中人脸 bbox，则从背景图裁剪出 insightface_crop 图片，用来和摄像头 CaptureImage 对比；裁剪失败只记录状态，不影响主链路。
  • 如果 DATABASE_URL 可用，则调用 recognition_repo.upsert_recognition_event()。
  • 写入失败不影响 P6S Ack、主飞书、attendance 和 shadow 链路，只记录错误日志并 fail-open。
  • 按 event_dedupe_key upsert，重复事件不会写出重复监控记录。

历史回填

python3 scripts/backfill_recognition_events.py \
  --date-from 2026-07-02 \
  --date-to 2026-07-05 \
  --root /var/lib/camera-face-guard/p6s_events \
  --apply
  • 默认 dry-run，只统计可回填数量、跳过数量、解析错误数量。
  • --apply 才写入数据库。
  • 支持 --date、--date-from、--date-to、--limit。
  • 每条记录读取 processing record JSON；如果需要补齐 InsightFace 裁剪图，则读取已保存的背景图片文件并按 bbox 裁剪。
  • 回填完成后输出 summary，包含 upsert 数、not_rechecked 数、缺图数、解析错误数。

查询路径

  • summary 接口使用 SQL 聚合，不扫描文件。
  • events 接口使用 SQL where + order + limit/offset 分页。
  • detail 接口按 event_dedupe_key 查询单行。
  • 图片接口仍按 relative path 从事件目录读取图片文件。

六、API 设计

所有 API 都挂在 /api 下，并依赖 require_admin。监控后台需要登录页面：优先复用现有 /login 和 JWT；如果当前服务没有可用登录页，本需求内补一个最小管理员登录页。页面加载数据时如果 token 过期，由前端跳转登录。

接口 参数 返回
GET /api/recognition-monitor/summary date=YYYY-MM-DD 日期、总数、分类计数、摄像头结果计数、recheck 状态计数、过滤原因 Top N。
GET /api/recognition-monitor/events date、classification、camera_result、recheck_status、reason、person、accepted、page、page_size 分页事件列表，默认按 event_time desc 排序。
GET /api/recognition-monitor/events/{event_key} 无；event_key 为 event_dedupe_key。 单条事件详情、完整 Gallery Top 5、阈值、质量 flags、图片引用、安全原始摘要。
GET /api/recognition-monitor/images relative_path=faces/... 管理员鉴权后返回图片 FileResponse。

图片接口安全

说人话：浏览器不能直接拿服务器磁盘路径去看图，也不应该拿一个公开裸链接。管理员打开页面后，前端带着登录 token 请求我们的后端；后端确认你是管理员，再去磁盘上读取那张图片，并把图片内容返回给浏览器。前端收到的是一段临时图片数据 blob，只在当前页面里展示，不暴露服务器真实路径，也不需要额外生成公开 token。

  • 请求必须带管理员 Bearer token。
  • 只接受相对路径，拒绝绝对路径和 ..。
  • 路径必须位于 P6S_EVENT_IMAGE_DIR 下。
  • 只允许 faces/、strangers/ 下的图片；不开放 raw JSON 图片正文。
  • 前端使用 fetch 带 Authorization 获取 blob，再设置 img.src=URL.createObjectURL(blob)。

七、前端页面设计

页面布局

  • 顶部导航：摄像头、识别监控、退出登录。
  • 统计卡片：总事件、疑似冲突、摄像头漏识别、同人确认、过滤数、no_face 数。
  • 筛选栏：日期、分类、人员搜索、过滤原因、摄像头结果、accepted。
  • 事件列表：背景图缩略图 + 摄像头结果 + InsightFace 结果 + 关键分数；缺图或未复核显示占位状态。
  • 详情弹层：背景大图、摄像头 CaptureImage、InsightFace 裁剪人脸图、bbox 信息、Gallery Top 5、阈值和原始安全摘要。

交互规则

  • 默认日期为 Asia/Shanghai 今天。
  • 默认 page_size 为 30，最大 100。
  • 默认每 10 秒刷新 summary 和第一页；用户打开详情弹层时暂停自动刷新列表。
  • 展示所有 FaceReco 记录，不因为缺图、无 face_recheck 或裁剪失败而隐藏。
  • 背景图在列表里先显示缩略图；点击缩略图打开详情弹层展示大图。
  • 筛选条件变更后重置到第一页。
  • 图片加载失败时显示“图片不可用”，不阻断列表渲染。

前端工具函数

function authHeaders() {
  return { Authorization: `Bearer ${localStorage.getItem("token")}` };
}

async function apiFetch(url) {
  const res = await fetch(url, { headers: authHeaders() });
  if (res.status === 401) logout();
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

async function loadImageBlob(apiUrl, imgEl) {
  const res = await fetch(apiUrl, { headers: authHeaders() });
  if (!res.ok) throw new Error("image unavailable");
  const blob = await res.blob();
  imgEl.src = URL.createObjectURL(blob);
}

八、异常处理

场景 处理
指定日期没有记录 数据库查询返回空 summary 和空列表，HTTP 200。
历史回填遇到单个 JSON 损坏 跳过该文件，在回填报告中增加 parse_error_count 和文件路径；不影响其他记录回填。
图片文件不存在 事件仍展示，图片接口返回 404，前端显示占位。
历史记录没有 face_recheck 标记为 not_rechecked，不在请求中补跑 InsightFace。
实时写入 recognition_events 失败 主事件链路 fail-open：继续 Ack、飞书和 attendance；记录错误日志，后续用回填脚本补写。
数据库不可用 监控 API 返回 500 和安全错误信息；不暴露连接串、密码或 SQL 细节。
token 过期 API 返回 401，前端清理 localStorage 并跳转 /login。

6 扩展本地验证，覆盖 row builder、upsert fail-open、backfill dry-run。 运行 python3 -m py_compile 覆盖新增模块和脚本；运行 python3 scripts/validate_p6s_event_flow.py 确认事件主链路不变。

Milestone 1 的 recognition_monitor.py 只提供入库所需的最小能力；summary/list/detail API、管理员鉴权图片代理、fetch blob 和页面展示统一留到 Milestone 2-3。

Milestone 3 只交付本地前端页面和页面路由，不执行 Alembic、不回填真实远程数据、不部署远程服务器。

Milestone 4 详细开发计划

步骤 任务 边界与验证
1 部署前保护检查：确认本地工作区状态、待部署 commit、远程服务状态、远程 env 和数据库迁移状态。 不打印真实密钥；部署前先备份 /etc/camera-face-guard/app.env 和记录当前 Alembic 版本；如果本地有未提交的计划外改动，停止确认。
2 使用既有部署脚本同步服务器代码和静态资源到 qypower-prod。 部署脚本需要把 recognition_repo.py、recognition_monitor.py、recognition_monitor router、Alembic 迁移和回填脚本纳入本地/远程检查；只部署识别监控后台代码，不修改摄像头配置、不修改脸库、不修改 InsightFace 模式、不切换 filter 或 verify_and_override。
3 在远程执行 alembic upgrade head，创建或升级 recognition_events 表。 远程 app.env 可能是 root-only，部署脚本允许用 sudo 读取 DATABASE_URL 到远程 shell 变量，但禁止打印真实连接串；迁移失败立即停止，不执行回填，并按迁移回滚策略处理。
4 对远程真实事件目录执行回填 dry-run。 先按单日小范围验证，再扩大到目标日期范围；dry-run 只输出统计，不写数据库、不生成新的裁剪图、不发送飞书。
5 确认 dry-run 统计合理后执行 --apply 回填。 apply 会写入 recognition_events 并按需补齐 InsightFace 裁剪图；运行报告需记录处理数、成功数、跳过数、错误数和错误类型，不保存图片正文或密钥。
6 重启远程服务并验证 /recognition-monitor。 确认服务 active、/api/docs、/camera、/recognition-monitor 可用，summary/list/detail/images 返回正常；用管理员登录页面查看真实日期数据和图片 blob。
7 部署后观察实时写入。 触发或等待新的 FaceReco 后确认 processing record、recognition_events、监控页面三者一致；主飞书、shadow 飞书、attendance、去重行为保持原样。

Milestone 4 的回滚优先级：先回滚代码或从导航隐藏页面；数据库新增表可保留不用；如果迁移必须回滚，先确认没有线上页面依赖后再 downgrade。

Milestone 5 详细开发计划

步骤 任务 边界与验证
1 基于真实使用反馈确认质量分析指标。 首版只从 recognition_events 现有字段派生趋势和差异，不新增人工复核流程，不新增业务写入表；如必须新增字段，先更新 LLD 和迁移计划。
2 扩展后端统计能力，增加按天趋势、过滤原因分布、摄像头与 InsightFace 差异分布、身份冲突列表。 查询仍基于 PostgreSQL 聚合和参数化 SQL；默认按日期范围限制结果，避免一次性扫描过大历史范围。
3 扩展前端质量分析视图。 页面应帮助快速看出“摄像头漏识别、摄像头识错人、模型过滤侧脸/模糊/无人脸、同人确认”的数量和样例；不展示内部日志噪音。
4 增加安全导出或复制摘要能力。 导出内容只包含安全摘要字段和图片代理相对引用，不包含图片正文、embedding、base64、webhook、secret 或服务器绝对路径。
5 完成质量分析验收和性能检查。 在远程真实数据上验证常用筛选和趋势查询响应时间；如数据规模增长导致慢查询，优先补索引或收窄默认日期范围，再考虑新增汇总表。

Milestone 5 是监控体验增强阶段，不改变实时识别决策，不启用 filter，不启用 verify_and_override，不对摄像头或脸库做任何写入。

  • 部署服务器代码、静态页面、Alembic 迁移和回填脚本；不修改摄像头配置、不修改人脸库、不修改 InsightFace 模式。

十三、已拍板结论

决策项 推荐选项 替代选项 影响
V1 是否建新表 已拍板：直接建 PostgreSQL 识别监控表，并用 Alembic 管理。 无。 避免未来再把历史 JSON 重新写库；首版上线需要包含迁移和回填步骤。
图片访问方式 已拍板：管理员鉴权图片代理 + 前端 fetch blob。 生成短期公开 token 链接。 推荐方案只有登录管理员能看图，不暴露服务器真实路径；前端实现略复杂但安全边界更清晰。
登录页面 已拍板：需要登录页面，优先复用现有 /login 和 JWT。 如果当前服务没有可用登录页，本需求内补最小管理员登录页。 管理员鉴权图片代理依赖登录态；没有登录页就无法安全确认看图的人是谁。
默认展示范围 已拍板：展示所有 FaceReco，缺图或未复核显示占位状态。 只展示有背景图且有 recheck 的记录。 推荐方案更像完整监控后台；替代方案更聚焦模型复核。
自动刷新间隔 已拍板：10 秒。 5 秒或手动刷新。 10 秒足够实时且压力更轻；用户打开详情弹层时暂停列表刷新。
人脸裁剪图 已拍板：服务端按 InsightFace bbox 从背景图生成裁剪图。 只显示 bbox 和尺寸信息。 页面可直接对比背景图、摄像头 CaptureImage 和 InsightFace 裁剪图；需要管理裁剪图文件生命周期。
人工复核状态 已拍板：不做人工复核。 V1 同时支持“已看/正确/错误”。 首版保持只读监控，不引入人工标记写入。
上线位置 已拍板：远程服务器 qypower-prod 上线，读取真实事件目录。 先只本地运行。 推荐方案能监控真实链路；本地只能看同步/测试数据。

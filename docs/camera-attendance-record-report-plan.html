Camera Face Guard / 技术方案

入场记录、日报与飞书去重

在现有 P6S 人脸识别事件链路上增加 PostgreSQL 数据层：每次识别都记录为入场事件；非陌生人 2 小时内不重复提醒；陌生人每次提醒；每天可生成会员、教练、员工、陌生人的到场统计和陌生人照片链接。

1. 目标与边界

本期要做
  • 每个真实人脸识别事件都写入 PostgreSQL，形成入场记录。
  • 记录人员类型：会员、教练、员工、陌生人、已匹配但未知分组。
  • 非陌生人 2 小时内重复识别时，只记录，不重复发飞书。
  • 陌生人每次识别都记录，并且每次发飞书。
  • 每天晚上 22:00 自动统计当天入场情况，写入日报快照表，并向飞书发送日报。
  • 日报标题固定为“每日入场情况统计”，内容按照日报快照表字段组织。
本期不做
  • 不做人脸向量、陌生人聚类或“同一个陌生人”的跨事件合并。
  • 不做复杂 BI 看板，仅提供日报所需的数据结构、自动生成和查询能力。
  • 不回填历史 JSON 事件，除非后续单独确认。
  • 不改变摄像头抓拍、识别、推送、脸库配置。

2. 核心规则

记录规则

每个真实 FaceReco 事件都插入 attendance_events。摄像头 HTTP 重试导致的同一事件重复投递不重复计入入场，只增加重复投递计数。

提醒规则

会员、教练、员工、未知已匹配身份，默认按同一人员 2 小时窗口去重。窗口内再次识别仍记录，但 should_notify=false。去重可通过独立开关关闭；关闭后仍写入事件流，但非陌生人也每次通知。

陌生人规则

陌生人不做 2 小时去重。只要识别到陌生人，就保存图片链接、写入记录、发送飞书。

图片规则

所有 FaceReco 事件都尽量保存抓拍图并生成 token 图片链接。非陌生人即使被 2 小时去重抑制，也仍然写入图片路径和链接，只是不发送飞书。

3. 数据流

摄像头向服务器推送 FaceReco 事件，服务端保留现有 raw JSON 落盘能力。
事件服务解析人员信息、分组、图片字段和 dedupe key。
只要 FaceReco 事件携带图片，无论是否匹配成功，都保存图片并生成 token 查看链接。
服务端写入人员主表；已存在则只更新姓名、分组、最近识别时间等轻量字段。
服务端写入 attendance_events，记录这次入场、图片、是否重复提醒、是否发送飞书。
如果启用提醒去重，则根据 2 小时窗口计算是否发送飞书；如果关闭提醒去重，则写库但每次发送飞书。发送结果写入 feishu_notifications。
每天 22:00 按日期聚合 attendance_events，写入 daily_attendance_reports。
日报写库成功后，按快照字段组织飞书消息，标题为“每日入场情况统计”。

4. 表结构设计

为了避免过度设计，本期只建 7 张业务表：三张已知人员表、一张陌生人表、一张入场事件表、一张飞书通知表、一张日报快照表。日报快照表为首版必选，用来固定每天 22:00 的统计结果和飞书日报内容。

6. 去重与提醒逻辑

6.1 非陌生人

同一 person_type + person_ref_id
如果 ATTENDANCE_NOTIFY_DEDUP_ENABLED=false：
  should_notify = true
  notification_suppressed = false
  发送飞书

如果 ATTENDANCE_NOTIFY_DEDUP_ENABLED=true：
查询过去 2 小时内是否存在 should_notify = true 且 notification_suppressed = false 的入场事件

如果不存在：
  should_notify = true
  notification_suppressed = false
  发送飞书

如果存在：
  should_notify = false
  notification_suppressed = true
  suppressed_reason = 'known_person_2h_window'
  dedupe_reference_event_id = 上一次提醒事件 ID
  不发送飞书

6.2 陌生人

person_type = 'stranger'
每次都：
  保存图片和 token 链接
  should_notify = true
  notification_suppressed = false
  发送飞书

6.3 图片链接全覆盖

所有 FaceReco 事件：
  如果事件携带 CaptureImage / BackgroundImage / recognizeImage
  保存图片和 token 链接
  写入 attendance_events.image_path / image_url

非陌生人：
  仍按 2 小时窗口决定 should_notify
  被去重抑制时不发飞书，但记录中仍保留图片链接

6.3 摄像头重复投递

如果相同 event_dedupe_key 再次到达，视为 HTTP 重试或缓存重放，不创建新的入场事件，不重复发送飞书，只更新 delivery_count。这和“2 小时内不重复提醒”是两个概念。

7. 日报生成与查询

日报每天 22:00 按 ATTENDANCE_REPORT_TIMEZONE 对当天 attendance_events 做实时聚合，统计口径是“入场次数”，不是唯一人数。聚合结果写入 daily_attendance_reports 后，再按快照字段发送飞书日报。

select
  event_time::date as report_date,
  count(*) filter (where person_type = 'member') as member_entries,
  count(*) filter (where person_type = 'coach') as coach_entries,
  count(*) filter (where person_type = 'staff') as staff_entries,
  count(*) filter (where person_type = 'stranger') as stranger_entries,
  count(*) filter (where should_notify = true) as notification_sent_count,
  count(*) filter (where notification_suppressed = true) as notification_suppressed_count
from attendance_events
where event_time >= :day_start
  and event_time < :day_end
group by event_time::date;

陌生人照片明细

select
  event_time,
  image_url,
  image_path
from attendance_events
where person_type = 'stranger'
  and event_time >= :day_start
  and event_time < :day_end
order by event_time;

10. 验证方式

本地 fixture

复用现有会员、教练、员工、未知已匹配身份和陌生人 fixture，验证 DB 写入、提醒策略和日报聚合。

去重测试

同一会员连续两次事件间隔小于 2 小时：两条入场都保存，第二条不发飞书并标记 notification_suppressed=true。

去重关闭测试

ATTENDANCE_DB_ENABLED=true 且 ATTENDANCE_NOTIFY_DEDUP_ENABLED=false 时，同一会员连续两次事件都写库、都发送飞书。

陌生人测试

同一天多个陌生人事件：每条都保存、每条都发飞书、日报列出每张照片链接。

日报测试

模拟 22:00 自动任务：当天统计结果写入 daily_attendance_reports，并发送标题为“每日入场情况统计”的飞书消息。

11. 风险与回滚

  • DB 不可用时，不应该影响摄像头 Ack 返回；首版建议记录错误并保留现有 raw JSON，避免摄像头重试风暴。
  • 表结构上线前先执行迁移脚本；回滚代码时不删除表，避免丢历史入场数据。
  • 飞书发送失败时，入场记录仍保存，通知表记录 failed，后续是否补发另行设计。
  • 日报飞书发送失败时，日报快照仍保留；首版只记录失败，不自动补发，避免重复日报。
  • 所有 FaceReco 图片链接仍沿用现有 token 机制，不在 DB 中保存 token 明文。
  • 图片链接全覆盖不改变非陌生人的 2 小时去重策略；被去重抑制的非陌生人仍写入图片路径和链接，但不发送飞书。

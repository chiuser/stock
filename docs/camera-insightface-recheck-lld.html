一、实现边界

本次开发范围
  • 新增 InsightFace 二次识别服务和质量过滤服务。
  • 新增服务器侧 gallery embedding 构建脚本和加载逻辑。
  • 在 FaceReco 图片保存后、写库/通知前接入二次判断。
  • 新增 shadow 飞书机器人消息模板和发送函数。
  • 新增本地 POC、fixture 验证和部署校验步骤。
明确不做
  • 不修改摄像头抓拍、识别、推送、录像、脸库配置。
  • 不接入 RTSP 连续视频流。
  • 不训练模型，不做活体检测，不展示年龄性别。
  • 不把 buffalo_l.zip、.onnx、人脸图片、gallery embedding 提交 Git。
  • 不改主飞书机器人密钥、图片 token 链接规则和日报格式。

摄像头写入禁止：本 LLD 的所有开发、测试、部署验证均不得调用任何 P6S 摄像头写接口。若后续确实需要调整摄像头配置，必须另起方案并获得明确授权。

二补充、已拍板结论

事项 结论 代码实现约束
首版上线模式 FACE_RECHECK_MODE=shadow 首版只发送 shadow 对比机器人消息，不改变主飞书、不改变 attendance_events 写入、不改变日报统计。
filter 模式过滤事件 不写入 attendance_events 只保存原始事件和处理记录。处理记录必须包含 face_recheck.status=filtered、face_recheck.reason、quality_flags，便于后续统计本地模型拦截数量和原因。
verify_and_override 允许以 InsightFace 有效识别结果纠偏摄像头结果 有效人脸高置信命中 Gallery 时按命中人员处理；有效人脸未高置信命中熟人时按陌生人处理。摄像头 known 与 Gallery 命中冲突时信任 InsightFace 纠偏；复核不可用时不得覆盖摄像头结果。
陌生人召回优先 熟人必须高置信确认 Gallery 相似度未达到熟人阈值时，不按熟人放行；如果该脸是有效人脸，则按陌生人触发。多人脸事件逐脸决策，多个有效未知脸按未知人脸数量触发陌生人通知。
复核不可用语义 不等同于确认陌生人 no_face、模糊、小脸、侧脸、低检测分、图片读取失败、模型异常都属于不可确认状态。可过滤主飞书和 attendance_events，但必须写入处理记录和监控表。
Gallery 构建失败 单人失败不阻断全量构建 失败人员写入 build_report。如果小明等关键测试人员失败，脚本应以明确错误提示停下来，等待修正图片或输入后再继续。
其余默认项 按技术方案和本文档默认建议执行 CPU-only、buffalo_l、模型不进 Git、embedding 不进 Git、默认 fail-open、侧脸和模糊阈值先用真实样本校准，启用后作为复核不可用过滤原因。

FinalRecognitionDecision 由 FaceRecheckResult 和摄像头原始结果合成，只在事件处理主链路内使用。它必须在写 attendance_events 和发送主飞书前生成；recognition_events / recognition_event_faces 只保存最终决策和逐脸事实，不能反向驱动主流程。

JSON 序列化要求

  • FaceRecheckResult.to_dict() 不包含 embedding 原始向量，不包含图片 base64，不包含机器人 token。
  • GalleryMatch.candidates 最多保留 Top 5 候选摘要，用于 shadow 飞书展示排名、人员、角色、组名和相似度。
  • FaceRecheckResult.thresholds 固化本次判断使用的阈值，便于消息里同时展示分数和判断口径。
  • 写入事件记录时字段名为 face_recheck。
  • 最终确认结果写入 final_recognition_decision，必须包含主触发、额外触发、被过滤人脸和原因，便于监控后台解释为什么某张脸没有触发主飞书。
  • shadow 机器人发送结果另写入 face_recheck_shadow_feishu，只保存 ok/status_code/text 摘要，不保存签名。

检测流程

def analyze_image(input: FaceRecheckInput, settings: FaceRecheckSettings) -> FaceRecheckResult:
    background = analyze_single_image(input.background_image_path)
    if should_fallback_to_capture(background, input.capture_image_path, settings):
        return analyze_single_image(input.capture_image_path)
    return background

def should_fallback_to_capture(result, capture_path, settings):
    if capture_path is None:
        return False
    reasons = set(result.reason.split(","))
    if "no_face" in reasons:
        return True
    if result.face_count == 1 and result.gallery_match:
        return result.gallery_match.similarity < settings.similarity_threshold
    return False

fallback 只改变 InsightFace recheck 选择的图片，不改变主飞书、attendance、摄像头原始结果或双图保存链路。处理记录中的 image_source 会显示最终使用的是 background 还是 capture。

七、质量过滤规则

质量门控由 FaceQualityGate 负责。它输出 flags，不直接发飞书、不写 DB。业务是否抑制由 FaceRecheckDecision 根据模式处理。

语义约束：no_face、低检测分、小脸、模糊、侧脸、图片读取失败、模型异常都属于 IF-NA（复核不可用），不属于 IF-U（有效人脸但 Gallery 未命中）。IF-NA 可以过滤掉主飞书和 attendance_events，但必须保留原始事件、处理记录、质量指标、过滤原因和监控后台记录。

构建规则

  • 身份信息只从 P6S 命名文件名解析，不再读取会员、教练、员工 CSV。
  • 不符合 I名称#S性别#T证件类型#M证件号码 的文件写入 build_report 并跳过，不猜测姓名或 ID。
  • 每张源图必须能被 InsightFace 检测到且只选一个主脸；无人脸、多脸、不可读或无 embedding 记为失败。
  • 低分、过小、模糊、侧脸等质量问题不阻断入库，写入 manifest 的 quality_flags 和 build_report 的 warning，避免 Gallery 覆盖率被首版阈值过度削弱。
  • 提取失败的人员写入 build_report，默认不中断全量构建，但报告中必须列出失败人员。
  • 同一 person_type + person_id 重复时停止，避免 gallery 索引歧义。
  • 同一 person_type + name 允许重复，但 shadow 对比时姓名一致只能作为“疑似一致”，最终仍保留 person_id 供回查。
  • 脚本默认输出到用户指定目录，不写入仓库。

摄像头结果对齐口径

  • 摄像头事件里如果返回姓名，则优先用 name 与 Gallery 命中姓名判断是否一致。
  • 摄像头事件里如果返回人员 ID 或证件号，则同时与 Gallery 的 person_id / credential_no 比对。
  • 当摄像头已识别为 known，且 Gallery Top1 与摄像头姓名或 ID 对齐时，accepted 相似度阈值使用 FACE_RECHECK_CAMERA_MATCH_SIMILARITY_THRESHOLD，当前用于 shadow 调参默认值为 0.30。
  • 当摄像头已识别为 known，但 Gallery Top1 是另一个人时，如果 Top5 中存在摄像头同人候选，且同人候选分数达到同人阈值、与 Top1 分差不超过 FACE_RECHECK_CAMERA_MATCH_GAP_THRESHOLD，则返回摄像头同人候选作为本次 GalleryMatch。候选列表仍保留原 Top5，便于 shadow 和监控后台解释。
  • 姓名一致但 ID 缺失时，shadow 消息标记为 name_matched；姓名或 ID 冲突时标记为 identity_conflict。进入 verify_and_override 后，冲突不再只记录，而是以高置信 Gallery 命中结果纠偏。
  • 目录角色决定 Gallery 身份类型：会员、员工、教练；不从文件名或摄像头返回字段反推角色。

发送规则

  • FACE_RECHECK_ENABLED=false 时不发送。
  • FACE_RECHECK_MODE=shadow 时每条 FaceReco 都发送 shadow 对比消息。
  • filter 和 verify_and_override 时仍发送 shadow 消息，便于追踪实际干预。
  • shadow 消息必须展示当前阈值，避免人工看分数时不知道是否达标。
  • Gallery 候选集最多展示 Top 5；只展示排名、姓名、身份类型、人员 ID、组名和相似度分数，不展示 embedding。
  • shadow 发送失败不影响主链路，记录摘要后继续。
  • 消息中不得包含 webhook、secret、base64 图片、embedding 原始向量。

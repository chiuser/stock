技术方案

P6S InsightFace 多人脸逐脸识别技术方案

把当前“每个事件只输出一个主脸”的复核方式，升级为“每个事件保存事件级事实，每张检测到的人脸保存一条 InsightFace 识别明细”。

适用范围：FaceReco 事件 主表：recognition_events 子表：recognition_event_faces 不修改摄像头配置

一、背景问题

事件 672 暴露了当前设计的核心问题：背景图里有两张人脸，摄像头识别的是右侧人脸“董小双”，InsightFace 也检测到了右侧人脸，并且右侧人脸 Top1 也是“董小双”；但当前代码只选择 面积 x 检测分 最大的一张脸输出，因此最终只展示了左侧“石峰”。

这不是 InsightFace 没看到右侧脸，而是我们的数据结构和输出结构把多人脸结果压缩成了一个 selected_face。压缩以后，多人场景会天然丢信息。

二、目标与非目标

目标

  • InsightFace 对 BackgroundImage 中检测到的所有人脸逐个识别。
  • 每张脸的处理逻辑与单脸一致：质量判断、Gallery TopN、阈值判断、候选集、crop 图都独立生成。
  • 数据库按父子表保存：一条摄像头事件对应多条 InsightFace 人脸结果。
  • 监控后台可以在事件详情中展示每张脸的框、crop、候选、分数和是否通过。
  • 历史记录可以通过回填/重刷脚本补齐子表，避免后续再迁移历史数据。

非目标

  • 不修改摄像头抓拍、推送、录像、脸库等配置。
  • 不在本次设计里启用 filter 或 verify_and_override 改变业务判断。
  • 不把 embedding 原始向量、base64 图片、Webhook 或密钥写入数据库。
  • 不新增人工复核写入流程。
  • 不把事件级字段重复铺满到每一张脸记录里。

三、核心数据关系

recognition_events 是事件父表，代表一次摄像头上报；recognition_event_faces 是人脸子表，代表这次事件里 InsightFace 检测到的每一张脸。

recognition_events 1 ---- N recognition_event_faces

recognition_events:
  事件 672，摄像头识别：董小双，背景图路径，Capture 图路径，事件时间，事件级分类

recognition_event_faces:
  事件 672 / background / face_index=0 / 左侧脸 / 石峰 / 0.441697 / accepted=true
  事件 672 / background / face_index=1 / 右侧脸 / 董小双 / 0.219165 / accepted=false

字段归属原则

信息类型 写入位置 原因
摄像头上报事实 recognition_events 例如事件时间、摄像头 event_id、摄像头识别结果、背景图路径、Capture 图路径。这些属于整次事件，不属于某一张脸。
InsightFace 逐脸结果 recognition_event_faces 例如 bbox、face_index、det_score、quality_flags、gallery_name、similarity、crop 路径。这些是每张脸独有的信息。
逐脸与摄像头结果的关系 recognition_event_faces 例如 camera_identity_status=name_matched 或 identity_conflict。它不是重复保存摄像头结果，而是保存“这张脸和摄像头识别人员之间的关系”。
事件级摘要 recognition_events 例如总人脸数、通过阈值的人脸数、是否存在摄像头目标候选。这些便于列表页和快速筛选。

四、冗余控制

这个设计会有少量必要冗余，但不会把事件字段重复到每张脸里。

子表不重复保存

  • 不重复保存 camera_serial_number。
  • 不重复保存 camera_person_name。
  • 不重复保存背景图和 Capture 图路径。
  • 不重复保存原始 JSON 路径。
  • 不重复保存飞书发送状态和入场记录状态。

子表必须保存

  • 每张脸自己的 bbox、位置和质量分。
  • 每张脸自己的 Gallery 命中和候选集。
  • 每张脸自己的 crop 图路径。
  • 每张脸和摄像头识别结果的关系判断。
  • 必要的 recognition_event_id 外键。

如果未来查询需要按时间筛选子表，可以通过 join 父表完成；如性能不足，再考虑在子表增加 event_date 这种可控冗余字段。

五、写入与读取职责

动作 负责模块 说明
实时写父表 p6s_events.py 处理完成后调用 recognition_monitor 沿用现有逻辑：保存 processing record 后 upsert recognition_events。
实时写子表 recognition_monitor / recognition_repo 从 face_recheck.faces 中提取逐脸结果，按 recognition_event_id + image_source + face_index upsert。
历史回填 backfill_recognition_events.py 或新增回填脚本 读取历史 processing record，必要时重新跑多脸识别，补齐父表和子表。
监控页读取 recognition_monitor API 列表页读父表摘要；详情页读父表 + 子表逐脸结果。
报表和分析读取 后续报表服务 按子表统计 Gallery 命中、多人脸冲突、摄像头陌生但 InsightFace 命中等。
实时业务判断不要依赖“先写 DB 再读 DB”。主链路应使用内存中的本次 FaceRecheckResult 做判断；数据库是事实记录、监控和后续分析来源。

六、图片处理策略

  1. 默认对 BackgroundImage 检测全部人脸并逐脸识别。
  2. 每张背景图人脸都生成一个 InsightFace crop，crop 绑定到对应子表行。
  3. 如果背景图没有检测到人脸，且存在 CaptureImage，则对 CaptureImage 执行同样的逐脸识别。
  4. 如果背景图检测到多张脸，且摄像头有 known 结果，可以额外处理 CaptureImage 作为 image_source=capture 的辅助行，但不覆盖背景图逐脸结果。
  5. recognizeImage 本期仍不纳入主流程，除非后续确认它比 Capture 图更适合作为摄像头目标脸。

八、上线方式

  1. 先实现 shadow 下的多脸逐脸记录，不改变主飞书和 attendance 行为。
  2. 部署后先对历史 7 月 4 日、7 月 5 日样本回填子表，验证事件 672 能展示两张脸。
  3. 监控页面确认稳定后，再讨论 filter 或 verify_and_override 如何使用多脸结果。
本方案不授权任何摄像头写配置。后续开发、测试、部署均不得调用摄像头写接口。
